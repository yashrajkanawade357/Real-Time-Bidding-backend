Live auctions where the highest bid always wins.

Hundreds of people can bid on the same lot in the same millisecond. Every bid is one database transaction behind a row lock, so the winner is decided by the data, never by whichever request happened to land last.

    How it stays correct

    One lock per lot

    Each bid takes the lot's row lock and is checked against the committed price, so bids queue and arrival order stops mattering.

    The database is the only state

    Servers hold sockets, never prices. A refresh, a reconnect or a brand-new server all read the same rows.

    Versioned events

    Every change carries a version. Clients ignore anything older than what they hold, so a snapshot and the live feed can't arrive out of order.

    Retries that don't double-bid

    Each bid has its own id. A client that lost its connection resends it, and the server returns the original outcome instead of bidding twice.

    Try to break it

    1. Bid against yourself. Open the floor in two windows, give each a different name, and outbid one from the other. The losing window says who outbid it, the moment the bid commits.
    2. Pull the plug. Open the floor with the network panel, choose Go offline, and queue a bid. Outbid yourself from the other window, then go back online. The queued bid is judged against the price now, and turned down.
    3. Watch the wire. The same panel lists every message on the socket with the version it carries, and which server instance you landed on.

    What's running

    On AWS: one EC2 instance behind CloudFront (HTTPS), nginx spreading visitors across two API instances, PostgreSQL alongside. The whole server builds itself from one boot script, and the same stack is tested in CI on every push.
